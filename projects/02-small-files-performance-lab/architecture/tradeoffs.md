# Trade-offs and scientific boundaries

- Many files increase filesystem listing/footer work and Spark planning/scheduling pressure, but Spark can pack multiple files into a task. Tiny local files often fit in OS cache; remote object stores add request latency and throttling absent here.
- Fewer files reduce metadata and can improve sequential reads/compression. Too few reduce read parallelism, enlarge retry work and may hurt selective queries. No universal speedup or optimal target is asserted.
- File-open cost is an estimated byte-equivalent used by the planner. maxPartitionBytes controls scan packing/splitting. Changing either may alter task packing without changing file layout. Keep both equal across layouts and compare alternative settings as separate experiments.
- Partition pruning excludes whole bucket directories; Parquet filter pushdown can skip row groups and column pruning reduces decoded data. Selectivity does not imply proportional runtime savings. Inspect PartitionFilters/PushedFilters in the saved plans. Our partition predicate is deliberately separate from the customer predicate.
- Region aggregation shuffles and has only four output groups. Shuffle/JIT/planning can dominate at quick size. AQE is disabled for a controlled baseline; production AQE must be benchmarked separately. No sort/clustering optimization is applied intentionally, though repartition can change row ordering and row-group statistics.
- Snappy, schema, logical partitioning and settings match. Small-file footers and changed encoding make physical totals differ despite identical rows. The JSON includes byte ratio and a >25% comparability warning; treat a warning as a confounder and increase rows before making a bytes-comparable claim.
- Per-bucket controlled writes reliably bound nominal targets but use multiple Spark jobs. Their overhead is part of measured compaction cost. A production partitionBy rewrite can be faster; this cost is implementation-specific.
- Validation warms storage before timing. Warmups, alternating order and medians reduce some startup/order bias without producing cold-cache evidence. No forced OS cache eviction. Query order is fixed. Five measurements are descriptive, not confidence intervals.
- The fingerprint is order independent and includes every column, but remains probabilistic. Query output SHA-256 is over sorted small aggregate records, not a full-dataset cryptographic digest. Integer cents avoid floating summation variance.
- Event logs capture executed counters for the whole application. No estimate is labeled measured scan I/O, and planned scan partitions are explicitly a proxy. Per-query bytes/task attribution is deferred rather than guessed.
- Economic sensitivity is an explicit hypothetical change to read savings and hourly rate. Cloud billing granularity, shared clusters, storage/request costs and operational risk require a separate deployment-specific model.

Independent JVM repetitions address application-to-application variability but do not flush OS caches or guarantee JIT steady state. Use paired per-run differences and retain within-run spread; do not treat all measured iterations from five applications as independent samples. Five applications remain a small descriptive study. Matching normalized operator plans is evidence of a controlled comparison, not equal scan work: file packing, row-group statistics, compression and scheduling may legitimately differ.

Recurring compaction is outside the one-rewrite processing-time break-even. Over a maintenance horizon, compare the sum of rewrite processing times with savings weighted by actual read frequency and query mix; then separately account for infrastructure billing and object-store request charges. Do not imply monetary profitability from a zero-rate time experiment.
